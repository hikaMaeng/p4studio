## 확인된 결함

### F1 · P1 · 요청 하나의 실패가 남은 소유자를 버리고 UNLOAD busy로 연결됨

[api.ts:301](../../../apps/studio/src/front/features/inference/api.ts)에서 일반 ERROR를 `fail(run, ..., "failed")`로 처리한다. `fail`은 queued/streaming 전체를 failed로 바꾸고, execute의 finally는 사용자가 이미 취소를 요청했을 때만 CANCEL을 기다린 뒤 연결을 닫는다. 실행 등록도 finally에서 제거된다. [control.ts:32](../../../packages/studio_domain/src/front/model/inference/cancellation/control.ts)의 cancel은 종료 상태에 아무 일도 하지 않는다.

반례: 접수된 요청 A와 보유 예산 때문에 거부된 요청 B. B refusal 하나를 보내면 A까지 failed가 되고, CANCEL0 상태로 연결이 닫힌다. 이후 `InferenceExecutions.unload`는 원래 owner를 취소하지 못한 채 UNLOAD를 실행한다. **AUD-01/02/03 RED**, 실제 Chromium **UI-02 재현**. 거부된 B의 미실행 증명을 A의 실패·정산 증명으로 사용할 수 없다.

P4의 [require_idle_unload](../../../../p4/layers/adapters/llamacpp/staged/adapter/src/v2/node/worker/shutdown.rs)는 requests/pending/releases/settlements/flights/owners/frontiers/receive/effects 등이 남으면 busy로 거부한다. UNLOAD는 암묵적인 CANCEL/drain이 아니다. 이 Studio 반례는 사용자 증상의 한 원인을 증명하지만 TUF의 모든 native/frontier 잔존 원인을 특정하지는 않는다.

### F2 · P1 · 자연 완료 OUTPUT를 RELEASE 완료로 취급하고 반환 연결을 닫음

[api.ts:336](../../../apps/studio/src/front/features/inference/api.ts)는 모든 요청의 terminal OUTPUT만 세어 run을 completed로 바꾼다. `waitForRun`이 끝나면 연결이 닫히며 completed 상태에서는 이벤트 consumer도 돌아가지 않는다. cancellation 모델은 RELEASE를 읽을 수 있지만 정상 실행 종료가 그 증거를 기다리지 않는다.

반례: 요청 1개, terminal OUTPUT 도착, RELEASE 미도착. 50ms 뒤 연결이 닫힌다. **AUD-04 RED**. P4 driver의 [completed==total && released==total](../../../../p4/tools/event-drive/src/run/inference.rs) 판정과 다르다. FINISH ACK는 transport 회수 증거이며 native/KV/request RELEASE 증거가 아니다. OUTPUT 이후 내부 해제가 반드시 실패한다고 주장하지 않으며, Studio가 정산 증거 없이 연결을 버리는 결함이다.

### F3 · P1 · 읽어 놓은 보유 예산을 웨이브 제출에 적용하지 않음

[llamaDispatchLimits](../../../packages/studio_domain/src/common/protocol/deployments/payload.ts)는 stage별 min `maxRequests`, `maxOutputTokensPerRequest`, `maxOutputTokens`를 반환한다. [api.ts:218](../../../apps/studio/src/front/features/inference/api.ts)는 요청 하나의 생성 토큰 상한만 사용하고, :359에서 5초마다 다음 웨이브를 보유량·RELEASE와 무관하게 전송한다.

반례: max_requests20, 동시10×10회/5초, 앞 요청이 아직 끝나지 않음. 10초에 PREFILL30개가 나간다. **AUD-07 RED**. 현재 기본 시험은 오히려 응답 없이 총100개 제출을 성공으로 요구하므로 이 결함을 검출하지 않는다. 허용된 시험을 20개로 축소하는 것이 요구의 해결은 아니다. 100개 보유가 가능한 LOAD profile을 준비하거나 명시적인 대기/용량 불충분 상태를 제공해야 한다.

### F4 · P1 · 일반 ERROR의 요청·correlation identity를 검사하지 않음

[control.ts:47](../../../packages/studio_domain/src/front/model/inference/cancellation/control.ts)의 일반 ERROR consumer는 취소를 요청하지 않았으면 false를 반환한다. 이후 [api.ts:301](../../../apps/studio/src/front/features/inference/api.ts)는 본문의 submission/owner/load/session 및 correlation/causation/source를 검증하지 않고 실행 전체를 실패 처리한다. OUTPUT·취소 응답 검증과 비대칭이다.

반례: 현재 OUTER를 target으로 하되 correlation=`old-operation`, 또는 request_id=`foreign-request`인 ERROR. 두 경우 모두 현재 run이 failed로 바뀐다. **AUD-05/06 RED**. 이는 인증 주장이 아니라 정상 route의 늦거나 잘못 귀속된 event에 대한 소비자 결함이다.

### F5 · P1 · 브리지 단절이 실행 모델에 전달되지 않아 running이 계속됨

[connection.ts:165](../../../apps/studio/src/front/p4/connection.ts)의 fail은 pending exchange만 reject하고 close한다. dispatch 기반 추론에는 pending exchange가 없고, connection/reception은 onEvent만 전달한다. [waitForRun](../../../apps/studio/src/front/features/inference/api.ts)은 상태를 50ms마다 볼 뿐 단절을 알 수 없다.

반례: 실제 BrowserP4Connection/Reception으로 binary SESSION_READY와 PREFILL1개를 통과시킨 뒤 WebSocket close를 발생시킨다. 60초 뒤에도 run=`running`. **AUD-09 RED**. 원격 GPU 없이 실제 browser transport 클래스의 응답 소비 경로를 사용했다. 종료 기한·무진행 timeout 또한 별도 계약이 없으며, LOAD timeout을 무조건 추론 제한으로 재사용하는 수정은 적절하지 않다.

### F6 · P2 · 실행 중 요청 상세에는 중지 버튼이 없음

### F7 · P1 · 적재 모델 삭제 버튼이 회수에 필요한 선언·generation 기록을 바로 폐기함

### F8 · P2 · 강제 초기화 뒤 노드 부재가 “언로딩 완료”로 투영됨

### F9 · P2 · 단일 노드 UNLOAD가 모델 UNLOAD의 실패 기록·시간 상한을 공유하지 않음

## MiMo 보유 한도와 현재 상태

- 과거 [deployment artifact](../../../target/mimo-150k-dflash-20261006/deployment.json)는 모든 stage의 `sequence_capacity=20`, `max_requests=20`, `max_input_tokens=150000`, `max_request_retained_bytes=67108864`, `max_output_tokens_per_request=8192`, `max_output_tokens=163840`다.
- P4 [RequestBudget::reserve](../../../../p4/layers/adapters/llamacpp/staged/adapter/src/v2/node/request_budget.rs)는 보유 요청 수·bytes·prompt_tokens·output_tokens의 **네 합계**를 동시에 검사한다. 이 어댑터의 [park_prefill_for_query / admission](../../../../p4/layers/adapters/llamacpp/staged/adapter/src/v2/node/worker.rs)는 예약 후 queued_prefills/pending에 넣는다. 실행 슬롯을 넘은 대기는 지원하지만 보유 예산을 넘으면 명시적으로 거부한다. 이 경로의 저장소는 Arc/Mutex, VecDeque/요청 map이며 요청의 디스크 spill/page-in 경로는 없다. 모델/KV/OS의 페이징 존재 여부 전체를 부정하는 주장이 아니다.
- **20은 코어 고정 상한이 아니다.** LOAD resource_profile이 정한 값이다. RequestBudget의 코드상 default는4096이지만 실제 LOAD의 profile이 이를 교체하므로 default만 바꿔도 이번 선언은 확대되지 않는다.
- 감사 중 읽은 [현재 HTTP 선언 snapshot](../../../target/lifecycle-audit-live-models.json)은 모든 stage의 `max_requests=100`, `max_output_tokens=819200`; sequence_capacity20와 input_tokens150000은 유지한다. **설정 저장과 현재 node의 그 용량 적재·100건 정상 실행은 다른 증거다.**
- 최신 선언은 failed. stage0/1은 load succeeded 이후 unload succeeded/absent, stage2는 `stage server exited while starting: exit code: 5`로 load failed/absent, stage3은 pending이다. 이전 20건 포화가 현재 초기화 실패의 원인이라고 하지 않는다. exit5의 native 원인/현재 원격 process 상태는 이번 조사에서 확인하지 않았다.
- 10×10/5초를 이전 요청 완료에 종속시켜 직렬화하는 대신, 그 부하를 수용할 보유 RAM 예산을 LOAD 전에 준비한다. count100뿐 아니라 요청 UTF-8/토큰 총량, 생성 예약100×per-request-cap, completion/terminal/RELEASE 저장 예산을 함께 검증해야 한다. sequence_capacity와 GPU KV를100으로 같이 늘릴 필요는 없다.

## 브랜치·워크트리 정리

- **p4studio만** 정리했다. 다른 저장소의 브랜치나 원격 프로세스는 이번 UI 조사 권한으로 삭제하지 않았다.
- local/remote heads는 main 하나. 감사 정리의 SHA는 `1cfc8bf...`, 이후 다른 채팅의 모델 상세 커밋으로 양쪽 SHA는 `6b83fd6...`가 됐다. 기존 기능 브랜치8개 커밋을 유지했고 커밋되지 않은 파일은 main working tree에 그대로 남겼다.
- codex/connection-teardown의 unique2 commits와 변이 dirty 파일, ignored 시험 자료는 `F:/dev/p4studio-backups/20261006-lifecycle-audit/`의 verified all-refs bundle와 tgz로 보존했다. unique2 commits를 검사 없이 main 코드에 합치지는 않았다.
- 최초 정리 뒤 p4studio git worktree 목록은 `F:/dev/p4studio` 하나였다. 마무리 중 다른 채팅이 `C:/Users/hika0/.codex/worktrees/loaded-model-details-deploy/p4studio`를 배포용으로 생성했다. 해당 작업 종료 후 Git 목록이 다시 기본 checkout 하나이고 C의 해당 경로도 존재하지 않는 것을 확인했다. C의 공통 worktrees 디렉터리 전체가 빈 것은 아니다. 그 안의 `.git` 파일을 확인한 결과 P4/NDX의 다른 저장소 worktree가 남아 있다. 사용자가 이 다른 저장소도 포함하는지 확인을 요청했으며, 그 작업의 브랜치·변경은 이번 p4studio 정리로 삭제하지 않았다.
- Git remove가 Windows에서 Directory not empty로 일부 파일을 남겼다. 추가 재귀 삭제는 자동 승인 검토가 정책상 차단했고 상세 사유는 제공되지 않았다. **안전한 대안으로 남은 디렉터리를 backup 아래 remaining-*에 이동**했다. 원래 `p4studio-connection-teardown`, `p4studio-connection-teardown-mutation` 두 경로는 존재하지 않는다. backup은 복원 자료이며 Git worktree 등록이 아니다.

## 수정 순서와 남은 검증

1. F1/F2/F4/F5의 공통 owner 원장부터 닫는다. 출력 결과와 pending settlement를 분리하고, 오류 후에도 정확한 제출·부분 출력·원래 반환 route를 보존해 CANCEL/drain/RELEASE 또는 unknown recovery로 이어간다.
2. 100건 부하를 받을 실제 LOAD profile과 per-model 총량을 준비한다. 기존 owned 자원이 없어야 재설정하며 unrelated 메모리·원격 프로세스를 무조건 종료하지 않는다. profile 확대 후 새 LOAD/SESSION 정상 응답을 증명한다.
3. 모든 상세 화면에 live stop/settlement 상태를 제공하고, 모델 기록 삭제는 회수 권한·실패 이력을 보존하는 명시적 동선으로 바꾼다. model/node UNLOAD의 deadline과 영속 결과를 통일한다.
4. 단조 revision/agent 작업 lease 및 [복구 계획](../../../docs/agent-recovery-plan.md)의 강제 회수·재기동 기능을 구현한다. 정상 UNLOAD, 관측 부재, 강제 회수, 재기동 완료를 별도 증거로 표현한다.
5. TUF와 MiMo에서 같은 generation/artifact의 정상 출력, CANCEL/terminal/RELEASE, stage별 정상 UNLOAD/native 회수까지 실기로 검증한다. **이 마지막 수용은 미실행**이다.
